# Database

PostgreSQL stores UUID primary keys generated by SQLAlchemy. Creation and event timestamps use timezone-aware columns. User-facing calendar dates are stored as dates calculated in the user's timezone. Keep historical local dates stable when the user changes timezone.

| Table | Purpose and key constraints |
| --- | --- |
| users | Unique normalized email and Argon2id password hash |
| user_settings | One settings row per user, with a timezone and week start from 0 (Monday) to 6 (Sunday) |
| goals | Owner, optional target date, optional completion time |
| projects | Owner and optional same-owner goal |
| tasks | Owner and optional same-owner project. Scheduled date supports daily and weekly range queries, separate from the due timestamp |
| habits | Owner and optional archive time |
| habit_logs | One completed entry per habit per local date. Ordered dates support streak calculations |
| focus_sessions | Owner, indexed start time, and optional end time strictly after start |
| daily_statistics | One row per owner and local date. Nonnegative activity totals and optional score from 0 to 100 |
| evening_reflections | One row per owner and local date, with notes and optional mood from 1 to 5 |
| refresh_sessions | Owner, absolute expiration, optional revocation time |
| refresh_credentials | Unique SHA-256 token digests with at most one unconsumed credential per session |

User deletion cascades to owned records. Deleting a habit or refresh session cascades to its logs or credentials. Projects and tasks can be unlinked before their parent goal or project is deleted. Composite foreign keys enforce that linked rows belong to the same account. Composite unique constraints supply the referenced owner and ID pairs. Ordered indexes support owner-scoped schedules, habit history, focus queries, and expired-session cleanup.

Future recommendations, achievements, notifications, XP, and accountability records can reference stable users and domain UUIDs with their own lifecycles and authorization rules.

## Phase 2 migration

Revision `0002` adds descriptions and update timestamps to goals, projects, and tasks. Existing update timestamps are backfilled from creation time. Existing completed goals receive progress 100, with other goals starting at 0. Goal status derives from its completion timestamp. Project status derives from its archive timestamp, and task status derives from its completion timestamp.

The migration adds project date bounds, task schedule timestamps, and an optional same-owner task-to-goal foreign key. PostgreSQL checks enforce valid progress, completion consistency, and schedule ordering. A goal or project referenced by another record must be unlinked before deletion. Downgrading to `0001` preserves Phase 1 rows and removes Phase 2 fields and constraints.

## Phase 3 migration

Revision `0003` extends the existing habit and log tables. It backfills update timestamps from creation time, gives legacy logs a count of 1, and initializes legacy habits as daily with a target count of 1. A legacy habit starts on the earlier of its UTC creation date and first stored local log date. Existing UUIDs, ownership, and log dates are preserved.

Weekdays are stored as a seven-bit mask. Checks enforce valid combinations of frequency, weekdays, weekly quota, and count bounds. The existing unique owner/habit/date key prevents duplicate log dates and supports ordered history queries. The owner-scoped habit foreign key cascades on permanent deletion. No streak aggregates are stored. Downgrading to `0002` preserves habit and log rows while removing Phase 3 fields.

## Phase 4 migration

Revision `0004` adds focus session states, session types, planned minutes, task links, and interval history. A partial unique index enforces one unfinished session per owner. Each session can have at most one open interval. Durations are derived from timestamps. A composite task foreign key clears only the task ID on deletion, preserving ownership and focus history. [PostgreSQL foreign-key actions](https://www.postgresql.org/docs/18/ddl-constraints.html)

Legacy focus rows become completed when they have an end timestamp and active otherwise. Each gets one interval using its original timestamps. If any account has multiple unfinished legacy rows, migration stops and rolls back. Review the affected owners with the query below. Reconcile redundant open rows by recording verified end timestamps that are after their start times, leaving at most one open row per owner before rerunning the migration.

```sql
SELECT user_id, count(*) AS unfinished
FROM focus_sessions
WHERE ended_at IS NULL
GROUP BY user_id
HAVING count(*) > 1;
```

Schedule migration during a maintenance window because its preflight locks the focus table through backfill. Downgrade to `0003` retains the original session rows and start/end timestamps. Phase 4 state, task associations, and pause intervals are lost on downgrade.

## Phase 5 storage

Phase 5 requires no schema migration. Reflections use the existing `evening_reflections` table and unique owner/date constraint. Daily reports read source records directly. The existing `daily_statistics` table is reserved for future snapshots and is untouched by these endpoints.

## Phase 6 AI usage

Revision `0005` adds one usage row per owner and UTC day. A row lock serializes request counts and token reservations across workers before outbound calls. The lock is released during provider I/O. Reported token counts replace reservations when available. Unreported attempts retain their reservation for that day, and identical summarized inputs reuse validated selections or fall back while a request is pending or failed. Stored selection data is limited to hashes, bounded action codes, and ordinal task references. No raw prompts or provider responses are stored. Downgrading removes the usage rows and leaves earlier tables intact. Operators can prune expired rows by the indexed date after their reporting window.

## Production database operations

Revision `0006` creates shared `request_rates` buckets. Its time-first primary key supports pruning by minute. Schedule pruning as a database maintenance job, for example hourly with `DELETE FROM request_rates WHERE "window" < floor(extract(epoch from now()) / 60)::bigint - 1440`. Schedule `ai_usage` pruning according to the reporting window. Set separate policies for expired refresh sessions, logs, and encrypted backups. Preserve user records under the applicable retention policy.

Use a dedicated migration role that owns the application schema. Give the runtime role `CONNECT` on the database and `USAGE` on the schema. Grant application-required table privileges and read-only access to `alembic_version`. For a fresh install, create both roles with SCRAM passwords using psql's `\password`, set schema ownership, and grant table privileges after migrating. Repeat the necessary grants after future migrations. The runtime role needs no database creation, superuser, or schema ownership privileges. A hosted database outside the private Compose network should use TLS with certificate verification.

Each app process uses `DB_POOL_SIZE` regular connections and up to `DB_MAX_OVERFLOW` extra connections. Budget the aggregate across processes below PostgreSQL capacity and reserve connections for operations. Pool checkout, connection, query, and readiness limits are in `.env.example`. The Alembic process uses the migration URL when supplied and has no application statement deadline. Run migrations as a single operation within a maintenance window when required. PostgreSQL transactional DDL rolls back failed revisions that remain in a transaction. Confirm the current revision and logs before retrying. Restore or reverse a migration only after testing the recovery path.

### Backup and restore drill

Schedule a custom-format logical dump at a frequency that meets your recovery point objective. Put backups in encrypted, access-controlled off-host storage and monitor backup age and restore duration. Keep the PostgreSQL 18 client tools available. On Windows, use `pg_dump --file` to write binary archives.

```powershell
# Substitute your PostgreSQL host, backup role, and source database.
pg_dump -h localhost -U backup_role -d disciply --format=custom --file=disciply.dump
pg_restore --list disciply.dump
# Use a new database name on an isolated or recovery PostgreSQL instance.
createdb -h localhost -U recovery_owner disciply_restore_test
pg_restore -h localhost -U recovery_owner -d disciply_restore_test --exit-on-error --single-transaction --no-owner --no-privileges disciply.dump
psql -h localhost -U recovery_owner -d disciply_restore_test -c 'SELECT version_num FROM alembic_version;'
```

Use an administrative connection and `pg_dump --file` inside the database container when the database is private to Compose. Copy the finished archive out with `docker compose cp`. Keep archive credentials out of arguments and logs by using PostgreSQL's password prompt or protected passfile. Back up role and grant definitions separately, and reapply intended permissions before promotion. Verify representative records, database ownership, Alembic revision, and readiness on the restored database. A logical dump is a point-in-time snapshot and does not provide continuous recovery.
